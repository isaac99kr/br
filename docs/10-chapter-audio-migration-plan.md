# 성경 전체 장별 음성 생성 및 신규음성 전환 계획

작성: 2026-10-23. 상태: **계획 작성 완료, 전체 배치 생성·플레이어 교체·배포는 아직 실행하지 않음.**

## 1. 목표와 범위

성경 전체를 `번역본 × 책 × 장` 단위 MP3와 절별 시간 JSON으로 제작한다. 날짜별 성경읽기와 모아 읽기의 「신규음성」은 같은 장별 자산과 같은 재생 엔진을 사용한다. 일정이나 모아 읽기 범위가 달라져도 음원을 재합성하지 않는다.

- 최종 대상: 현재 서비스의 `krv`(개역개정), `rnksv`(표준새번역), 각각 66권 전체. **krv부터 완성하고 rnksv를 이어서 진행**하는 것을 기본 순서로 한다.
- Angelina, 한국어, 속도 0.9, 합성 12단계, 장 안내 뒤 0.5초, 절 사이 0.12초, 모노 MP3 96kbps를 유지한다.
- 「신규음성」의 기존 일차별 MP3·일차별 매니페스트 의존성을 전부 교체한다. 지원 여부를 일차 번호로 판단하지 않는다.
- 별도 「음성듣기」의 브라우저 TTS는 유지한다. 이번 요청의 교체 대상은 신규음성이며, 기존 TTS와의 동시 재생 방지 규칙도 유지한다.
- 읽기 완료 처리, 진행 기록, 일정 순서, 본문 데이터의 의미는 바꾸지 않는다. 재생 종료가 읽기 완료를 자동 처리하지 않는다.
- 이 문서는 기존 `09-new-audio-playback-plan.md`의 신규음성 지원 범위·일차별 자산 설계를 대체하는 후속 계획이다.

- rnksv: 66권, 1,189장, **31,102개 절 항목**.

## 3. 작업을 끊는 단위와 예상 자원

**완료 단위는 한 장, 운영 단위는 최대 20장 또는 약 60분, 검수 단위는 한 권**으로 한다. 두 번역본을 동시에 합성하지 않는다.

창1의 절 수 비율로만 환산하면 한 번역당 합성 약 22시간, 재생 약 70시간, MP3 약 3GB 수준이다. 긴 절, 모델 로딩, 장별 편차, 오류 재시도, 청취 시간은 반영하지 않은 거친 계획값이다. 실제 일정 약속으로 사용하지 않는다. 두 번역의 글자 수와 낭독 길이도 다르므로 단순 두 배로 확정하지 않는다.

현재 float WAV를 절별 파일과 전체 장 WAV로 모두 보관하면 한 번역당 약 90GB 수준까지 커질 수 있다. 전체 두 번역을 무조건 모두 보관하기 전에 디스크 정책이 필요하다.

- 10~20개 대표 장 벤치마크 후 번역별 예상 시간·용량·남은 시간을 다시 계산한다.
- 초기 운영은 2스레드, 한 번에 한 장. 주간은 1스레드도 선택 가능하지만 실행 도중 바꾸면 해시와 재사용 범위가 달라지는 현재 구조를 먼저 개선한다.
- 60분 제한은 새 장 시작 여부를 제어하는 소프트 제한이다. 진행 중인 한 장을 저장·검증하고 멈추므로 정확히 60분에 끝나지는 않는다.
- 사람이 듣고 확인하는 시간은 합성 시간과 따로 관리한다.

## 4. 0단계 — 대량 생성 전에 해결할 사항

### 4.1 본문 전수 감사

`audit_chapter_sources.py`를 추가하여 번역별 책·장·절 목록, 정리된 본문 해시, 빈 본문, 번호 비연속, 비정상 제어문자, 예상 밖 표기를 출력한다.

현재 생성기는 창1 이외에도 1부터 최댓값까지 연속된 절 번호를 요구한다. 번역별 실제 데이터가 이 조건에 맞는지 확인하고, 정상적인 합절·번호 공백과 데이터 손상을 구분한다. **빠진 절을 임의 생성하거나 번호를 당겨 맞추지 않는다.** 화면에 표시하는 본문과 동일한 절 ID 체계를 사용한다. 읽을 텍스트가 없는 절은 별도 상태·재생 정책을 정하고 테스트한다.

### 4.2 생성조건과 재사용 범위 고정

현재 해시에 생성기 파일 전체, 성경 책 JSON 전체, 스레드 수가 들어가므로 검증 코드만 고쳐도 재합성이 발생하고, 한 장 수정이 같은 책의 다른 장에도 영향을 준다. 전체 생성 전에 다음으로 나눈다.

- `synthesisHash`: 해당 장의 실제 정리 본문, 안내 문구, 스타일, 모델 파일/리비전, SDK·합성 의존성, 합성 로직 버전, 난수 정책 등 음성에 영향을 주는 조건.
- `assemblyHash`: 절별 WAV 해시, 무음 정책, 인코딩 조건, 시간 스키마.
- 검증 도구 버전과 검증 결과: 합성 해시와 별도 관리. 검증 수정 때문에 합성하지 않는다.
- 스레드·운영체제 등 실행 정보는 기록한다. 스레드 변경의 호환성은 벤치마크 후 결정하며, 확인 전에는 같은 배치 안에서 고정한다.
- 원본 책 전체 해시는 출처 추적용으로 남기되, 장의 캐시 무효화는 해당 장 입력을 기준으로 한다.
- 이미 생성된 창1 샘플은 그대로 보존한다. 새 규격으로 가져올 때 조건 검증을 통과한 파일만 등록하고, 해시 이름만 바꾸어 재사용하지 않는다.

### 4.3 장 길이와 예외 보강

시119처럼 긴 장, 한 절짜리 범위, 여러 문장으로 긴 절, 단락 제목, 번역별 예외를 확인한다. 디코딩 결과와 결합 파형을 한꺼번에 메모리에 올리는 현재 구현의 최대 메모리를 측정하고 필요하면 스트리밍 검증으로 바꾼다.

### 4.4 디스크 보관 정책

- 검증 완료 후 `chapter.wav`는 재결합 가능한 임시 산출물로 분류해 정책에 따라 정리한다.
- 검수 중인 배치의 절별 WAV는 보존한다. 검수 완료·최종 파일 백업 이후 오래된 WAV를 정리하는 별도 명령을 제공한다.
- WAV를 정리한 완료 장은 MP3·JSON·해시·검증 기록으로 완료 판정한다. 현 생성기의 ‘모든 WAV를 먼저 읽는 재실행 경로’를 수정해야 한다.
- 디스크 부족은 새 장 시작 전에 감지해 중단한다. 임계값은 대표 장 최대 작업 공간과 남은 디스크로 결정한다.
- 정리 명령은 대상 목록을 먼저 보여주며 MP3·JSON·검수 기록을 삭제하지 않는다. 실패/중단 파일은 성공 파일과 구분한다.

완료 기준: 전수 감사 결과 설명 가능, 대표 장 자동 검증 통과, 창1 청취 및 경계 확인, 해시/보관 규칙 확정.

## 5. 1단계 — 중단·재개 가능한 배치 운영 도구

`generate_chapters.py`를 추가한다. 아래 명령은 **계획 중인 인터페이스이며 아직 존재하지 않는다.**

```bash
# 합성하지 않고 대상과 기존 완료 여부 확인
tts/.venv/bin/python tts/scripts/generate_chapters.py --translation krv --books 창 --chapters 1-10 --dry-run

# 최대 20장 또는 60분 운영, 한 번에 한 장
tts/.venv/bin/python tts/scripts/generate_chapters.py --translation krv --max-chapters 20 --max-minutes 60 --threads 2

# 같은 명령으로 다음 미완료 장부터 계속
tts/.venv/bin/python tts/scripts/generate_chapters.py --translation krv --max-chapters 20 --max-minutes 60 --threads 2

# 실패한 대상만 재시도
tts/.venv/bin/python tts/scripts/generate_chapters.py --translation krv --retry-failed --max-chapters 20 --threads 2
```

필요 기능:

1. 번역·책·장 기준의 고정 작업 목록과 합성 프로필을 저장한다.
2. `pending / running / generated / validated / reviewed / published / failed`를 구분한다. 파일이 있다는 것과 청취 검수 완료는 다르다.
3. SQLite 등 트랜잭션 저장소에 작업 상태·시도 횟수·오류·소요 시간·해시·경로를 기록한다. 터미널 세션이나 대화 기록을 상태 저장소로 쓰지 않는다.
4. 프로세스 잠금과 작업 소유자를 확인하고, 실제 실행 중인 작업을 중단 작업으로 오인하지 않는다. 종료된 실행의 `running`은 파일 검사 후 재개한다.
5. Ctrl+C는 진행 중인 단위를 안전하게 중단하고 다음 실행에서 완료 WAV를 재사용한다. 별도 stop 요청은 현재 장 완료 후 멈춘다.
6. 일시 오류는 제한된 재시도만 수행한다. 본문 오류는 해당 장 실패로 기록한다. 모델/디스크 등 공통 오류 또는 연속 실패 3회는 배치를 멈춘다.
7. 완료 장을 건너뛰고, `--force`는 반드시 명시된 번역·책·장 범위에만 허용한다. 전체 강제 재생성을 기본값으로 제공하지 않는다.
8. 상태 명령으로 완료/실패/남은 장, 최근 처리 속도, 예상 잔여 시간, 디스크 사용량을 확인한다.
9. 재부팅·터미널 종료 후에도 같은 명령으로 재개한다. 장시간 실행은 로그 파일과 `caffeinate` 등 macOS 절전 방지 방법을 안내한다. 자동 예약은 별도 선택 사항이다.

완료 기준: 실제 중간 중단·재개, 실패 대상 재시도, 중복 실행 차단, 완료 장 무합성 재검증을 시험한다.

## 6. 2단계 — 대표 장 파일럿과 생성 순서

### 파일럿

krv의 창1·2, 시23·119, 요1·3, 행8·20, 롬1, 계22를 우선 생성한다. 기존 창1은 검증된 재사용 가능성을 먼저 확인한다. rnksv에서는 창1·시119·행20을 우선 비교한다. 총량 벤치마크와 절 번호 예외 검사 결과에 따라 대표 장을 추가한다.

특히 아래를 청취한다.

- 각 장 첫 절/마지막 절, 긴 절, 고유명사가 많은 구간.
- 창1:1, 창1:10, 창1:1-10처럼 잘라 들었을 때 다른 절 말소리 혼입 여부.
- 장 안내와 본문 전환, 문장 누락·반복·발음·억양.
- 두 번역의 본문과 실제 음성이 일치하는지.

### 전체 생성

파일럿 승인 후 krv의 창세기를 완성하여 첫 권 단위 운영을 검증한다. 이어서 신약 전체 → 구약의 창세기 외 나머지 순으로 진행한다. 같은 책 안에서는 장 순서대로 생성한다. 기존 220~246일차 자료를 새 규격으로 교체할 수 있도록 신약을 앞당기는 순서다.

krv 전체 완료 후 rnksv도 창세기 → 신약 → 나머지 구약 순으로 진행한다. 실제 제공 범위는 시간표가 아니라 검증된 장의 커버리지로 결정한다.

각 세션 종료 시 `이번 완료 장 / 실패 장과 이유 / 청취 대기 / 다음 명령 / 남은 예상 시간 / 디스크 여유`를 기록한다. 20장 기준 두 번역 약 120회 분량이지만 긴 장과 시간 제한에 따라 실제 횟수는 달라진다.

## 7. 3단계 — 장별 배포 계약과 매니페스트

로컬 작업 폴더를 웹에서 직접 참조하지 않는다. 검증된 장의 MP3·JSON만 공개 자산으로 복사/업로드한다. WAV, 가상환경, 모델, 로그는 배포하지 않는다.

경로 예시:

```text
audio/chapters/<releaseId>/krv/GEN/001/<assetHash>.mp3
audio/chapters/<releaseId>/krv/GEN/001/<assetHash>.json
audio/chapters/<releaseId>/manifest.json
audio/chapters/current.json
```

- 장별 JSON은 기존 `schemaVersion`, ms 및 sample 경계, MP3 해시를 유지한다. 필드를 바꾸면 스키마 버전과 호환성 정책을 명시한다.
- 매니페스트는 번역·책·장 → MP3/JSON URL, 두 파일 해시, 합성 프로필, 길이, 크기, 절 목록, 공개 상태를 연결한다.
- `current.json`은 검증된 불변 릴리스 매니페스트를 가리킨다. 재생 세션 동안 하나의 릴리스만 사용하여 이전 MP3와 새 JSON이 섞이지 않게 한다.
- MP3와 JSON 업로드 → 실제 제공 경로 검증 → 매니페스트 → current 포인터 순으로 공개한다. 롤백은 이전 포인터로 한다.
- 서빙되는 JSON/MP3의 해시를 배포 파이프라인에서 검증한다. 브라우저는 스키마·장·번역·단위·경계·버전 연결을 검사한다. 재생 전에 전체 MP3를 해싱하려고 항상 다운로드하지 않는다.
- 지원 범위는 manifest에 등록된 장 기준이다. `day >= 220` 같은 조건을 제거한다.

전체 음원이 여러 GB 규모이므로 기존처럼 전부 `public/audio`에 Git 추적하여 넣는 방식을 기본으로 삼지 않는다. **웹 앱은 현재 호스팅을 유지하고 음원은 별도 정적 저장소/CDN에 두는 구성을 우선 검토**한다. 공급자는 아직 결정하지 않는다. 실제 용량, 전송 비용, HTTPS, CORS, Range 요청/206 응답, MIME, 캐시, 백업·롤백 조건을 확인한 뒤 결정한다. 요금·서비스 한도는 선택 시점에 공식 자료로 확인한다.

공개 배포 준비 시 기존 프로젝트의 본문·음성 배포 조건도 다시 확인한다. 이는 로컬 생성 계획과 별개이며 이 문서 작성으로 업로드나 유료 서비스 계약을 실행하지 않는다.

## 8. 4단계 — 성경읽기와 모아 읽기의 공통 재생 모델

### 공통 큐 생성

`chapterAudio.ts`(장 자산 로더/스키마 검사)와 `audioQueue.ts`(읽기 범위 → 재생 큐)를 분리한다. 날짜별 화면과 모아 읽기는 동일한 `loadVersesForRange` 결과와 범위 경계를 넘긴다.

재생 단위는 `{occurrenceId, translationId, book, chapter, startVerse, endVerse, startSample, endSample, audioUrl, timingUrl}` 형태를 기본으로 한다. 안내 구간은 별도 항목으로 표현한다.

- 입력 순서와 중복을 보존한다. 같은 장이 다시 등장해도 임의 정렬·중복 제거하지 않는다.
- 연속 절은 같은 파일의 연속 구간으로 묶되 원래 `segmentStart` 경계는 보존한다.
- `창1:1-10, 창1:11-20`: 같은 MP3의 서로 다른 두 구간을 사용한다.
- `행8:1-13, 행8:26-40, 행8:14-25`: 입력 순서대로 앞으로 갔다가 뒤로 돌아온다.
- 같은 절을 두 번 요청하면 두 번 재생한다. 강조와 스크롤은 절 ID뿐 아니라 화면상의 occurrence/index로 구분한다.
- a/b 표기는 현재 본문 로더처럼 절 전체를 재생한다. 반절 타이밍이 없으므로 임의로 나누지 않는다.
- 장 경계나 새 입력 범위 시작에서는 저장된 장 안내 구간을 재생한다. 부분 범위는 안내 후 선택한 첫 절로 이동하며 선택하지 않은 앞 절은 읽지 않는다. 기존 segmentStart 안내 규칙과 일치시키고 파일럿에서 청취 확인한다.
- 마지막 선택 절의 `endSample`에서 끝내고 다음 항목으로 이동한다. 다음 절과 그 뒤의 불필요한 구간은 포함하지 않는다.

### 재생 엔진의 핵심 결정

단순 `HTMLAudioElement`의 `timeupdate` 이벤트로 끝 절에서 정지시키는 방식은 다음 절이 섞일 수 있다. 먼저 파일럿에서 다음 두 경로를 비교한다.

1. **부분 구간 기본 후보: Web Audio의 장별 디코딩 버퍼와 구간 예약 재생.** start/end를 시간 JSON에서 계산하고 예약 종료한다. 배속·일시정지·재개 시 소스 노드를 다시 만들며 AudioContext의 시간으로 진행을 계산한다.
2. 전체 장은 HTML audio 스트리밍을 사용하는 최적화를 검토할 수 있지만, 두 재생 경로의 상태·배속·강조 규칙은 하나의 컨트롤러로 통일한다. 부분 구간을 이벤트 타이머만으로 정확하다고 간주하지 않는다.

44,100Hz 샘플 인덱스를 AudioContext의 다른 샘플레이트 버퍼 인덱스로 그대로 사용하면 안 된다. 원본 sampleRate로 초를 계산하고 디코딩 결과의 샘플레이트·리샘플링을 반영한다. 모바일 Safari/Chrome에서 MP3 지연과 구간 경계를 검증한다.

현재 장과 다음 장 정도만 메모리에 보관하는 LRU 캐시를 사용한다. 긴 장의 디코딩 시간과 메모리를 측정한다. 선택 구간 정확도와 모바일 메모리를 동시에 만족하지 못하면 대량 배포 전에 재생 전략을 재설계한다. 숨김 탭의 타이머가 계속 정확히 동작한다는 전제를 두지 않는다. 백그라운드 재생 보장은 별도 요구로 남긴다.

### 상태와 UX

- loading → ready → playing ↔ paused → ended, 그리고 error 상태를 분리한다.
- 사용자 첫 클릭으로 오디오 컨텍스트를 활성화하고 자동재생 제한을 처리한다.
- 큐 전체 진행 시간과 파일 내부 시간을 구분한다. 탐색/배속 변경 시 큐 항목과 현재 장 시간을 함께 계산한다.
- 현재 절은 `[start, end)`로 판정한다. 절 사이 무음에서는 절 강조를 해제하고 장 문맥은 유지한다.
- 번역/일정/모아 읽기 범위 변경, 패널 닫기, 화면 이탈 시 기존 재생과 비동기 로딩을 취소한다. 오래된 응답이 새 큐를 덮어쓰지 않게 한다.
- 일부 장이 없으면 누락 범위를 알려주고 전체 큐의 재생을 시작하지 않는 것을 초기 정책으로 한다. 없는 구절을 조용히 건너뛰거나 다른 번역/브라우저 TTS로 자동 대체하지 않는다.
- 네트워크 재시도는 현재 항목에서 가능하게 하고 오류 시 강조·재생 상태를 정리한다.
- 기존 재생/일시정지/정지/배속/절 이동/스크롤/크롬 숨김을 유지한다. 읽기 완료는 사용자가 처리한다.

## 11. 실제 착수 순서와 중간 인계

- **작업 A:** 창1 청취, 본문 전수 감사, 해시/재사용/보관 정책 보강. 완료 전 대량 생성하지 않는다.
- **작업 B:** 배치 생성기·상태 명령 구현, 중단/재개 시험, 대표 장 벤치마크. 이때 전체 ETA와 디스크 계획 갱신.
- **작업 C:** 장별 매니페스트/스키마, 공통 큐, 구간 재생 프로토타입. 성경읽기와 모아 읽기를 함께 검증.
- **작업 D:** 창세기 전체 생성·검수, 두 화면 통합, 모바일 경계 검증.
- **작업 E:** krv 신약/나머지 구약을 20장/60분 세션으로 진행. 장별 검수·커버리지 갱신.
- **작업 F:** rnksv 전체를 같은 절차로 진행. 번역별 예외를 독립 확인.
- **작업 G:** 음원 호스팅 선택 및 릴리스 준비, 전체 범위 테스트, 전환·롤백 검증.
- **작업 H:** 전면 전환 후 이전 일차별 자산/코드 정리, 운영 안내 업데이트.

각 작업 종료 시 `tts/work/batches/<runId>/`에 상태/로그/요약을 남기고, 다음 세션은 상태 명령으로 이어간다. 문서나 대화에 ‘어디까지 했는지’ 수동으로 기억하는 방식에 의존하지 않는다.

## 12. 이번 계획의 기본 결정과 후속 결정 지점

기본 결정은 두 번역 최종 지원, krv 우선, Angelina 유지, 순차 2스레드 합성, 20장/60분 운영 단위, 브라우저 TTS 유지, 신규음성은 두 화면 공통 장별 엔진 사용이다.

실행 중 근거를 모아 결정할 항목은 본문 예외 처리, 모바일 구간 재생 구현, 음원 호스팅/예산, 청취 검수 범위와 공개 일정이다. 이 항목들은 각각의 단계에서 필요한 결과를 준비한 뒤 결정하며, 지금 계획 작성을 위해 전체 작업을 멈추지는 않는다.
