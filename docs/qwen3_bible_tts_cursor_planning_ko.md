# 성경읽기 사이트 Qwen3-TTS 음원 기능 기획서

## Cursor AI 사전 기획 요청서

> **작업 원칙:** 지금은 구현하지 않는다. 먼저 기존 프로젝트를 분석하고,
> 기술 검증과 용량 산정을 포함한 상세 기획안을 작성한 뒤 사용자 승인을
> 기다린다.

## 1. 프로젝트 목표

현재 React 기반 성경읽기 사이트에 **로컬에서 Qwen3-TTS로 생성한 한국어
성경 음원**을 추가한다. 웹 브라우저의 내장 TTS는 사용하지 않는다. 모든
사용자는 배포된 동일한 음원 파일을 재생하며, 브라우저나 기기에 따라
음색이 달라지지 않아야 한다.

음원은 개발 PC에서 생성·검수한 후 정적 파일로 배포한다. 서비스 운영
중에는 TTS 서버나 백엔드 API를 호출하지 않는다. 사이트는 기존처럼
React + GitHub Pages 기반의 정적 사이트로 유지한다.

### 필수 사용자 기능

-   성경 번역본 선택: **개역개정**, **표준새번역**
-   음성 선택: **남성**, **여성**
-   재생 / 일시정지 / 정지
-   재생 속도 조절: 최소 0.75x, 1.0x, 1.25x, 1.5x, 2.0x 검토
-   음원 재생에 맞춰 현재 읽는 성경 본문이 자동으로 스크롤되도록 구현
-   현재 읽는 절 또는 문단을 시각적으로 표시
-   사용자가 본문을 직접 스크롤하거나 특정 절을 선택하면 해당 위치부터
    재생할 수 있는 방식 검토
-   기존 스케줄에 따른 날짜/항목 선택, 읽기 상태(안읽음 → 읽기 시작 → 완료),
    끝까지 읽으면 자동 완료, 사용자가 완료 체크를 해제하면 안읽음으로
    변경하는 기존 동작 유지
-   읽기 상태와 날짜별 진행 정보는 기존 결정대로 `localStorage`에 저장
-   모바일 세로 화면을 우선 지원
-   사이트는 브라우저 종류와 무관하게 동일한 생성 음원을 재생

## 1.1 기존 스케줄을 단일 기준으로 사용한다

- 프로젝트에 이미 별도의 성경 읽기 스케줄이 있다. **365일 기준을 새로 만들거나 가정하지 않는다.**
- 스케줄의 실제 데이터, 항목 수, 날짜/일차 ID, 각 항목에 연결된 책·장·절 범위를 코드와 데이터에서 직접 조사한다.
- 음원 생성 대상, 파일 매핑, UI 선택 항목, 용량 산정은 모두 기존 스케줄을 그대로 따른다.
- 기존 스케줄의 항목 수나 구조를 변경·정규화·재생성하지 않는다. 스케줄 데이터에 없는 읽기 날짜/항목을 임의로 추가하지 않는다.
- 스케줄이 여러 파일 또는 여러 단계로 구성되어 있으면 현재 앱이 실제로 사용하는 기준과 연결 관계를 문서화한다.
- 기존 스케줄의 항목 수와 기간을 확인하기 전에는 전체 음원 수나 전체 용량을 확정하지 않는다.

## 2. 기존 구조와 제약을 먼저 조사할 것

코드를 수정하기 전에 저장소 전체를 조사하고, 현재 상태를 요약한다.

1.  React/Vite 프로젝트 구조와 현재 GitHub Pages 배포 설정
2.  `import.meta.env.BASE_URL` 또는 저장소 하위 경로 처리
3.  기존 성경 읽기 스케줄 데이터, 성경 TXT 파일의 위치·인코딩·책/장/절 파싱
    구조
4.  번역본별 원문 파일이 실제로 모두 존재하는지 확인
5.  기존 날짜별 읽기 상태와 `localStorage` 키/데이터 구조
6.  현재 본문 화면과 자동 스크롤 구현 상태
7.  저장소의 실제 크기, GitHub Pages 배포 용량, 빌드 산출물 크기
8.  이미 구현된 기능을 중복 구현하거나 불필요하게 재작성하지 않을 방법

**중요:** 표준새번역 본문 파일이 프로젝트에 실제로 있는지 확인한다.
없다면 임의로 생성하거나 인터넷에서 무단으로 가져오지 말고, 입력 자료가
필요한 항목으로 기획서에 기록한다. 개역개정·표준새번역의 복제, 음성
변환, 공개 배포 권한도 확인 항목으로 둔다.

## 3. 음성 생성 모델 및 라이선스 조사

Qwen3-TTS를 우선 후보로 조사하되, 이름이나 과거 설명만 믿고 구현하지
않는다. 공식 저장소와 각 모델의 모델 카드에서 아래 항목을 확인하고, 조사
날짜와 출처 URL을 기획서에 기록한다.

-   현재 사용 가능한 Qwen3-TTS 모델 변형과 한국어 지원 여부
-   `CustomVoice`, `VoiceDesign` 등 필요한 모델 유형과 용도 차이
-   한국어에서 실제로 사용할 수 있는 남성·여성 화자 목록
-   화자 이름, 발음 품질, 음색 일관성, 긴 본문 생성 시 안정성
-   모델 코드 라이선스와 **모델 가중치 라이선스**가 같은지 여부
-   생성 음원의 공개 배포 및 광고 수익이 있는 사이트에서의 사용 가능성
-   화자 음성 또는 음색의 이용 조건에 별도 제한이 있는지
-   로컬 실행 요구 사양, GPU/VRAM, CPU 실행 가능 여부, 필요한
    Python/CUDA 버전
-   오프라인에서 모델을 다운로드한 뒤 반복 생성할 수 있는지
-   모델 버전이 바뀌면 기존 음원과 음색이 달라질 수 있는지

라이선스가 불명확한 항목은 가능하다고 단정하지 말고 `확인 필요`로
표시한다. 공식 저장소, 모델 카드, 라이선스 원문을 우선한다.

공식 저장소 후보: https://github.com/QwenLM/Qwen3-TTS

## 4. 음성 톤을 비교하고 최종 선정하는 절차

본격적으로 전체 음원을 만들기 전에 **음성 스타일 선정 단계**를 별도
작업으로 설계한다.

### 4.1 비교할 스타일

같은 모델 버전, 같은 화자, 같은 테스트 본문을 사용하고 지시문만 바꾸어
비교한다. 각 스타일의 실제 생성 결과를 청취한 뒤 선택할 수 있어야 한다.

-   **A. 편안하고 차분한 낭독:** 따뜻하고 안정적이며 장시간 듣기 편한 톤
-   **B. 따뜻하고 생동감 있는 이야기 낭독:** 가족 청취자를 대상으로 하며
    적당한 감정과 자연스러운 리듬
-   **C. 또렷하고 정돈된 오디오북 낭독:** 발음과 문장 구분이 명확하고
    과장되지 않은 톤
-   필요하다면 사용자가 추가 스타일을 쉽게 등록할 수 있는 구조

목표는 어린이에게도 흥미롭고 성인·어르신에게도 편안한 **가족용 성경
오디오북**이다. 지나치게 느리거나 기계적인 낭독, 과장된 영화 예고편식
연기, 만화 같은 음색은 피한다. 음악은 기본 낭독을 방해하지 않아야 하며,
배경음악은 초기 필수 기능으로 단정하지 말고 별도 선택 기능 또는 후속
단계로 비용·용량·라이선스를 비교한다.

### 4.2 테스트 문장과 선정 방법

-   두 번역본에서 실제 사용 권한이 확인된 동일 길이의 테스트 구간을
    준비한다.
-   내레이션 문장, 고유명사, 숫자/단위, 쉼표가 많은 문장, 문장이 긴
    구간을 포함한다.
-   남성/여성 후보 화자별로 같은 스타일 비교를 진행한다.
-   가능하면 각 후보를 WAV로 생성한 뒤 동일한 방식으로 청취하고, 품질
    검수 후 압축본도 비교한다.
-   평가표 항목: 한국어 발음 정확도, 자연스러움, 따뜻함, 감정 절제,
    장시간 청취 편안함, 음색 일관성, 생성 속도, 파일 용량.
-   사용자에게 후보별 음원을 쉽게 재생하고 A/B 비교 및 최종 선택을
    기록할 수 있는 간단한 로컬 검수 도구를 제안한다.
-   선택한 모델·버전·화자·지시문·생성 설정을 버전 관리 가능한 설정
    파일로 고정한다.

**현재 단계에서 임의로 음성 톤을 확정하지 않는다.** 테스트 절차와 산출물
형식을 설계하고 사용자가 샘플을 듣고 결정할 수 있게 한다.

## 5. 음원 크기와 음질: GitHub Pages 제한을 최우선으로 검토

목표는 음질을 불필요하게 손상하지 않으면서 정적 음원 전체가 배포 제한
내에 들어가는 것이다. 실제 본문 길이를 기반으로 측정하고, 근거 없는 용량
추정만으로 설계를 확정하지 않는다.

### 5.1 비교할 오디오 포맷

다음 선택지를 실제 샘플로 비교하도록 계획한다.

-   WAV: 원본 품질 기준 및 검수용. 일반 배포에는 용량이 너무 클 수 있음.
-   MP3: 폭넓은 호환성과 적절한 압축률을 제공하는 기본 후보
-   Opus: 더 작은 용량이 가능할 수 있으나 브라우저 지원과 재생 호환성을
    검증해야 함

MP3를 기본 후보로 두되, 샘플 청취와 용량 측정 결과를 보고 결정한다. 음성
낭독에는 음악이 포함된 경우와 순수 음성인 경우의 압축 특성이 다를 수
있으므로 실제 음원으로 시험한다. 인코딩 도구(예: FFmpeg)의 버전과 명령행
설정을 기록한다.

### 5.2 반드시 계산할 용량

다음 모든 조합을 포함해 전체 예상치를 계산한다.

-   번역본 2종: 개역개정, 표준새번역
-   성별 음성 2종: 남성, 여성
-   기존 스케줄에 포함된 전체 읽기 항목
-   선택한 분할 단위와 실제 음원 길이
-   파일별 메타데이터/매니페스트 및 빌드 산출물

총 조합은 기본적으로 **2 × 2 = 4개 음원 세트**다. 예를 들어 각 번역본에
남녀 음성이 각각 존재하므로, 한 가지 조합만 계산하지 않는다.

실제 테스트 음원의 초당 비트레이트와 길이로 아래를 산정한다.

-   하루 평균 용량
-   번역본 1종 × 성별 1종의 전체 용량
-   4개 세트의 총 용량
-   GitHub 저장소 크기와 Pages 배포 크기의 차이
-   향후 수정 음원 및 재생성 파일이 차지할 공간
-   1GB 등 적용되는 Pages 제한에 대한 여유 공간

현재 GitHub Pages 제한과 정책은 공식 문서에서 다시 확인하고, 문서 URL과
조사 날짜를 기록한다. 음성 파일을 모두 Pages에 넣을 수 있는지 판단하기
전에는 대규모 생성 작업을 시작하지 않는다.

### 5.3 용량 초과 시 대안

1.  인코딩 설정과 오디오 포맷을 비교해 음질 대비 용량을 최적화한다.
2.  하루 단위, 장 단위, 절/문단 단위 중 적절한 분할 전략을 비교한다.
3.  Pages 제한을 초과하면 오디오 파일만 별도 정적 호스팅에 둘 수 있는지
    검토한다. 다만 외부 서비스의 무료 정책·중단 가능성·CORS·대역폭
    제한을 조사하고 사용자 승인 없이 선택하지 않는다.
4.  Git LFS가 GitHub Pages의 정적 배포 음원 호스팅 문제를 자동으로
    해결한다고 가정하지 않는다.
5.  사용하지 않는 모델 체크포인트와 WAV 원본을 웹 배포 디렉터리에
    포함하지 않는다. 원본은 로컬 제작 공간에 보관하고 배포에는 최종
    음원만 포함한다.

## 6. 음원 파일 분할 및 매니페스트 설계

음원과 본문을 동기화하려면 하루 전체를 하나의 긴 파일로 만들지, 장/절
또는 문단 단위로 나눌지 검토한다.

각 방식의 장단점을 비교한다.

-   **하루 단위 파일:** 파일 수가 적지만 본문과 절 단위 동기화가 어렵고,
    특정 절로 이동하기가 불편할 수 있음
-   **장 단위 파일:** 파일 수와 탐색 편의성의 균형이 좋을 수 있지만,
    절별 자동 스크롤을 위해 시간 정보가 필요
-   **절/문단 단위 파일:** 현재 읽는 텍스트를 정확히 표시하고 해당
    절부터 재생하기 쉽지만 파일 수와 요청 수가 늘어남

우선 요구사항을 가장 잘 충족하는 방식을 추천하되, 실제 용량과 파일 수,
브라우저 재생 안정성을 근거로 선택한다. 절별 파일을 택한다면 파일마다
재생 시작/종료 이벤트로 스크롤을 동기화할 수 있는지 검토한다. 긴
파일이라면 절별 타임스탬프를 어떻게 생성·검수할지 제시한다.

매니페스트에는 최소한 다음 정보가 필요하다.

-   번역본 ID
-   읽기 날짜/일차 ID
-   책·장·절 식별자
-   음성 성별 및 화자 ID
-   파일 경로(상대 경로)
-   파일 길이 및 선택적으로 절별 타임스탬프
-   생성 모델 버전, 생성 설정 버전
-   생성 완료/검수 상태

파일 경로는 GitHub Pages 하위 경로 배포를 고려해
`import.meta.env.BASE_URL` 기준으로 해석한다. URL을 코드에 하드코딩하지
않는다.

## 7. 본문 자동 스크롤과 오디오 플레이어

음원과 텍스트가 어긋나지 않도록 재생 모델을 명확히 설계한다.

-   재생 중 현재 읽는 절/문단에 활성 표시를 적용한다.
-   현재 절이 화면 밖으로 벗어나면 부드럽게 자동 스크롤한다.
-   재생 일시정지/정지 시 자동 스크롤도 적절히 멈춘다.
-   사용자가 특정 절을 누르면 해당 절부터 재생하는 동작을 검토한다.
-   재생 속도 변경이 현재 파일과 이후 파일 모두에 반영되어야 한다.
-   파일을 넘어 다음 절/파일로 전환할 때 재생 속도와 선택한 번역본/성별
    음성을 유지한다.
-   사용자가 날짜나 번역본을 바꾸면 이전 재생을 정리하고 올바른 파일을
    불러온다.
-   모바일 Safari 및 Android Chrome에서 재생, 속도 변경, 백그라운드/화면
    잠금 시 동작을 검증한다. 브라우저가 허용하지 않는 동작을 보장한다고
    문서화하지 않는다.
-   읽기 상태가 기존의 스크롤 기반 완료 판정과 충돌하지 않도록 한다.
    오디오가 끝났다는 이유만으로 읽기 완료 처리할지, 텍스트를 끝까지
    스크롤한 경우에만 완료 처리할지 정책을 비교하고 추천안을 제시한다.
-   `localStorage`의 기존 데이터와 키를 임의로 삭제하거나 호환성 없이
    변경하지 않는다.

## 8. 음원 생성 파이프라인

개발 PC에서 재현 가능한 생성 파이프라인을 설계한다.

1.  입력 성경 텍스트를 파싱하고 책/장/절 식별자를 부여한다.
2.  번역본별 원문과 기존 읽기 스케줄의 매핑을 검증한다.
3.  모델 버전, 화자, 스타일 지시문, 생성 파라미터를 읽는다.
4.  음원을 생성하고 파일로 저장한다.
5.  WAV 원본과 배포용 압축 파일을 분리한다.
6.  길이·샘플레이트·인코딩·파일 크기 검사를 수행한다.
7.  빈 파일, 생성 실패, 누락된 절, 중복 파일을 탐지한다.
8.  재생 검수 대상 목록을 만들고 사람의 청취 검수를 거친다.
9.  매니페스트와 용량 리포트를 생성한다.
10. 최종 승인된 음원만 정적 사이트의 배포 경로로 복사한다.

재실행 시 이미 생성된 파일을 무조건 다시 생성하지 말고, 원문 해시·모델
버전·설정 버전이 동일한 경우 재사용할 수 있는 방안을 제시한다. 오류 발생
시 재시작 및 일부 파일만 재생성하는 기능도 계획에 포함한다.

## 9. 품질 검수 기준

다음 항목을 자동 또는 수동으로 검수한다.

-   본문 누락/중복/순서 오류
-   한국어 고유명사와 성경 용어 발음
-   문장 끝이 잘리거나 과도하게 늘어지는 현상
-   비정상적인 침묵, 갑작스러운 음량 변화, 클리핑
-   음색과 속도의 일관성
-   두 번역본의 본문 매핑 정확성
-   남성/여성 선택과 실제 재생 음원 일치 여부
-   음성 파일과 화면의 현재 절 동기화
-   선택한 배속에서 파일 전환이 자연스러운지
-   모바일에서 재생과 자동 스크롤이 안정적인지

자동 음성 인식으로 원문과 생성 음성을 비교하는 검수는 보조 수단으로만
사용하고, 중요한 발음 오류는 사람이 직접 들어 확인하도록 한다.

## 10. Cursor AI가 먼저 제출해야 하는 산출물

현재 단계에서는 코드를 구현하지 말고 다음을 작성한다.

1.  **현재 프로젝트 분석 보고서:** 기존 구현, 파일 경로, 재사용할 코드,
    미구현 항목
2.  **기술 선택 비교표:** 모델/화자/포맷/분할 방식/재생 구조별 장단점
3.  **라이선스 및 권리 확인표:** 모델 코드, 가중치, 화자, 성경 번역본,
    생성 음원의 배포 조건
4.  **음성 스타일 테스트 계획:** A/B/C 지시문, 테스트 본문, 청취·평가
    방법
5.  **용량 산정 보고서:** 샘플 실측값, 4개 전체 세트 예상치, Pages
    제한과 여유 공간
6.  **파일 구조와 매니페스트 설계**
7.  **UI/UX 변경 계획:** 번역본·성별 선택, 플레이어, 배속, 현재 절 표시,
    자동 스크롤
8.  **단계별 구현 계획:** 단계, 작업 항목, 영향받는 파일, 완료 기준,
    테스트 방법, 위험 요소
9.  **사용자 결정이 필요한 질문 목록:** 반드시 필요한 질문만 추려서 제시

각 권고에는 가능한 한 근거와 검증 방법을 포함한다. 확인하지 않은 사실은
사실처럼 쓰지 않는다. 특히 모델 라이선스, 화자 이용권, 성경 본문 배포권,
GitHub Pages 제한, 한국어 남녀 화자 지원을 추측으로 확정하지 않는다.

## 11. 구현 단계 제안

기획서에서 아래 단계의 순서와 완료 기준을 구체화한다.

-   **Phase 0 --- 기존 프로젝트 및 권리 조사**
-   **Phase 1 --- 한국어 남녀 음성/낭독 스타일 샘플 생성**
-   **Phase 2 --- 음질·용량·생성 속도 비교 및 스타일 선정**
-   **Phase 3 --- 소량의 본문으로 음원 생성/매니페스트/플레이어 검증**
-   **Phase 4 --- 기존 스케줄 전체 4개 음원 세트 생성 및 검수**
-   **Phase 5 --- React UI 통합과 동기화 테스트**
-   **Phase 6 --- Pages 용량 검증 및 배포**

모든 단계를 한 번에 실행하지 않는다. 특히 기존 스케줄에 포함된 전체 음원 생성은 샘플
음질·용량·라이선스·배포 권한을 확인하고 사용자가 승인한 뒤에만 진행한다.

## 12. 작업 규칙

-   지금은 **기획과 조사만 수행**한다.
-   기존 코드를 변경하거나 음원 전체를 생성하지 않는다.
-   필요하다면 작은 샘플 테스트가 유용한지 계획서에 제안하되, 사용자
    승인 전에 대량 작업을 실행하지 않는다.
-   프로젝트의 기존 기능과 `localStorage` 진행 상태를 보존한다.
-   새로운 백엔드나 데이터베이스를 도입하지 않는다.
-   웹에서 재생되는 음원은 최종적으로 고정된 정적 파일이어야 한다.
-   계획서와 코드 변경 범위를 명확히 분리한다.
-   최종 결과는 `docs/bible-tts-plan.md` 또는 프로젝트에 적합한 기획
    문서 경로로 저장하고, 핵심 결정 사항과 미확정 항목을 요약해
    사용자에게 보고한다.

**최종 목표:** 자연스럽고 편안한 한국어 성경 낭독을 남성/여성 음성과 두
번역본으로 제공하고, 재생 속도 및 본문 자동 스크롤을 지원하면서 GitHub
Pages의 정적 배포 제약과 음원 용량을 만족하는, 재현 가능하고 검수 가능한
음원 제작 체계를 설계한다.
